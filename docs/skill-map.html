What do I run, and what does it need?

One agent harness across every project. Skills are grouped by when in the work you reach for them, and colored by what they depend on — because that is what decides whether a skill works in a fresh repo or needs a key in .agents/stack.yml first.

Nothing matches. The router's rule: when in doubt, invoke the skill anyway.

hook a PreToolUse hook blocks the call
tool-list the capability is absent from the agent
prompt the contract asks; nothing checks
read-only proposes, never mutates

The configuration ladder

Every general skill reads .agents/stack.yml instead of hardcoding your project. Each key you fill in unlocks the skills below it. A missing key is a supported state — the skill asks you, or refuses naming the key. It never guesses.

Which review do I run?

Four skills touch a pull request. The split is deliberate: the human maintainer owns delivery, Codex publishes reviews, and the responder posts fixes and replies.

Which decision skill?

One axis: which direction the work is moving. /next and /triage are complements, not alternatives — one looks forward at what to start, the other backward at what was left unfinished.

What the stack refuses to do

The refusals are the point. This harness was extracted from a repo that once carried 27 open PRs, 80 unmerged branches and 55 worktrees — every one of which started as a good idea. The missing constraint was never idea generation.

no auto-decide pipelineNothing chains reviews and answers their questions for you. Reviews surface decisions; you make them.
/land stops at the PRBranch, gates, atomic commits, open the PR. Merging is a human decision and routes nowhere.
the scope gate defaults to OUTAn idea with no citation in the scope doc is out of scope by default. It must argue its way in.
a merged PR is not gate evidenceShared verbatim by the retro and the release audit. Shipping code is not the same as passing a gate.
no activity metricsCommits, lines changed and PR counts are never scores. The retro refuses to compute them.
no criterion without a runnable checkAcceptance criteria name the command that verifies them, or they do not ship.
Canonical files live once, at <tier>/<name>/SKILL.md. Hosts and projects point at them and never restate the procedure — a second copy of a prompt drifts, and the drift stays invisible until two harnesses disagree about the same proposal. Project skills shadow stack skills of the same name; domain skills stay in their own repo.
