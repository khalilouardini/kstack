Delivery is now gated by a validator, not by rereading

This page is the reference artifact for explain-diff-html. It explains one change — the introduction of a hard gate on generated explanation pages — and it is also the executable version of the spec: it passes every check the gate applies.

What the system does now

Before, a generated explanation page was finished when its author had read it back. Now a page is finished when validate_explanation.py exits 0. Nothing about the writing step changed; what changed is that the author's judgment is no longer the last thing standing between a broken artifact and the reader.

The gate is stdlib-only Python, reads one file, and speaks in exit codes. It has no configuration and no network access, which means it produces the same verdict on the author's machine and on the reviewer's.

Why rereading was not enough

The failures worth catching are the ones invisible to whoever wrote the page. Three recur:

  • Assets that only exist on the author's machine. A stylesheet or font pulled from a remote host renders perfectly for the person who has it cached and silently degrades for everyone else.
  • Code samples with no white-space rule. The browser collapses every sample onto one line — and the page still looks plausible to the author, whose eye supplies the structure the markup lost.
  • A comprehension check that can be scored without comprehension. If the right option is reliably the longest one, or reliably in the same slot, the quiz measures pattern-matching.

None of these are caught by reading. All three are caught by a program.

How the gate works

One parse pass collects the material each check needs, then the checks run independently and accumulate into a report. Failures block; warnings are printed and do not affect the exit code.

  1. Step 1Read the file as text
  2. Step 2Parse once into title, ids, pre blocks, styles, scripts
  3. Step 3Run every check against that material
  4. ExitNon-zero if any check failed

The checks

CheckBlocks when
documentNo doctype, no closing tag, or an empty title — the signature of a truncated write
offlineA remote asset, an @import, or a network call in an inline script
code-blocksNo CSS rule targeting pre sets a preserving white-space
diagramsBox-drawing characters or ASCII art appear inside a pre
structureA required section is absent, or an anchor points at no id
quizThe question set is not five well-formed entries
quiz-positionOne slot holds three answers, or fewer than three slots are used
quiz-lengthThe right option is the single longest in over half the questions
quiz-leakMarkup reveals correctness before the reader chooses

Why outbound links are allowed but assets are not

An <a href> to a remote page is a reference: follow it or do not, the page still renders. A remote src is a dependency: without it the page is wrong. The offline check draws the line exactly there, which is why it inspects every element except a.

The quiz-data contract

Auditing a quiz requires it to be machine-readable, so the questions live in one JSON block and the option elements carry no correctness marker at all:

<script type="application/json" id="quiz-data">
[{"question": "...", "options": ["...", "..."], "answer": 2,
  "explanation": "...", "distractors": {"0": "the misreading this encodes"}}]
</script>

Two consequences follow. The answer field indexes the options exactly as emitted, so shuffling is an authoring-time decision and the page stays reproducible. And because correctness lives only in the JSON that the script reads on click, "do not leak the answer" becomes something a program can verify rather than something an author promises.

Running it

python3 validate_explanation.py /tmp/2026-01-01-explanation-slug.html
